# Architecture references

Go paths (`internal/`, `cmd/`, `migrations/`) are relative to `services/timesheet-core/`. Go tools run there, or from the repo root with `go -C services/timesheet-core`.

Sources verified live on 2026-10-09; the registry is the "Architecture sources" table in `.claude/skills/coding-standards/sources.md`. Each rule is a check against a design or ADR. ## AWS Well-Architected (`aws-well-architected`)

- **AWS-1** Every remote call has a timeout. Retries use capped exponential backoff with jitter and a maximum count, at one layer only. [AWS REL05-BP03](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_mitigate_interaction_failure_limit_retries.html), [Builders' Library: timeouts and retries](https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter)
- **AWS-2** Permanent errors (permission, configuration) and non-idempotent calls are not retried; repeated failures are monitored and alerted. [AWS REL05-BP03](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_mitigate_interaction_failure_limit_retries.html)
- **AWS-3** A mutation has a unique token (UUID or KSUID, never a timestamp), stored with a pending, completed or failed state, recorded atomically with the mutation, expired by TTL, passed downstream; duplicate requests are tested. [AWS REL04-BP04](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_prevent_interaction_failure_idempotent.html)
- **AWS-4** A retried request returns a semantically equivalent response, not "already exists"; the same token with different parameters is rejected; idempotency records have a bounded lifetime. [Builders' Library: idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)
- **AWS-5** Components follow bounded contexts: no domain entity library shared across contexts, and a new context is protected by an anti-corruption layer. [AWS REL03-BP02](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_service_architecture_business_domains.html)
- **AWS-6** Outbox: the entity and its outbox row are written in one transaction, nothing is emitted on rollback, order is kept by a sequence, and the consumer is idempotent because duplicates are possible. [AWS PG outbox#implementation](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html#transactional-outbox-implementation), [#issues](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html#transactional-outbox-issues)
- **AWS-7** An ACL guards each external system, has monitoring planned, and is declared temporary (recorded as technical debt) or permanent. [AWS PG ACL#applicability](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/acl.html#acl-applicability), [#issues](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/acl.html#acl-issues)
- **AWS-8** No long-term credentials in source or config files; the repo is scanned for secrets; secrets can be removed, replaced or rotated. Env vars are the accepted deviation D3. [AWS SEC02-BP03](https://docs.aws.amazon.com/wellarchitected/latest/security-pillar/sec_identities_secrets.html)
- **AWS-9** Static and dynamic security testing run in CI, an SBOM is produced, and the design states which findings block the pipeline. [AWS SEC11-BP02](https://docs.aws.amazon.com/wellarchitected/latest/framework/sec_appsec_automate_testing_throughout_lifecycle.html)
- **AWS-10** The design emits logs, metrics and traces in one standard way and masks sensitive data in them. [AWS OPS04-BP02](https://docs.aws.amazon.com/wellarchitected/latest/framework/ops_observability_application_telemetry.html)
- **AWS-11** Changes are small, frequent and reversible; failure and recovery procedures are tested, not assumed. [AWS OE principles](https://docs.aws.amazon.com/wellarchitected/latest/framework/oe-design-principles.html), [AWS reliability principles](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/design-principles.html)

## Azure Well-Architected and Architecture Center (`azure-well-architected`)

- **AZ-1** Keep it simple: just enough code, and critical-path components are separated from ones allowed to degrade. [Azure reliability#keep-it-simple](https://learn.microsoft.com/en-us/azure/well-architected/reliability/principles#keep-it-simple), [#design-for-resilience](https://learn.microsoft.com/en-us/azure/well-architected/reliability/principles#design-for-resilience)
- **AZ-2** Retries are finite, at most one immediate retry, never duplicated across layers, and their total latency fits the end-to-end budget; `Retry-After` is honoured. [Azure transient faults#avoid-anti-patterns](https://learn.microsoft.com/en-us/azure/well-architected/design-guides/handle-transient-faults#avoid-anti-patterns), [#determine-an-appropriate-retry-count-and-interval](https://learn.microsoft.com/en-us/azure/well-architected/design-guides/handle-transient-faults#determine-an-appropriate-retry-count-and-interval)
- **AZ-3** Interactive paths (Slack approval) use immediate or regular-interval retries; background work (outbox relay, weekly run) uses exponential backoff with jitter. [Azure transient faults#determine-an-appropriate-retry-count-and-interval](https://learn.microsoft.com/en-us/azure/well-architected/design-guides/handle-transient-faults#determine-an-appropriate-retry-count-and-interval)
- **AZ-4** Retry only where the full failure context is understood, and the design tests retry code under failure. [Azure Retry#general-guidance](https://learn.microsoft.com/en-us/azure/architecture/patterns/retry#general-guidance)
- **AZ-5** The ACL covers every external system the team doesn't control, holds translation only (no business rules or orchestration), validates and sanitises input, and logs with correlation IDs. [Azure ACL#context-and-problem](https://learn.microsoft.com/en-us/azure/architecture/patterns/anti-corruption-layer#context-and-problem), [#problems-and-considerations](https://learn.microsoft.com/en-us/azure/architecture/patterns/anti-corruption-layer#problems-and-considerations), [#when-to-use-this-pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/anti-corruption-layer#when-to-use-this-pattern)
- **AZ-6** Consumers aim for effectively-once: a stable deduplication key (not a correlation ID or a broker-generated ID), the marker committed with the side effects in one transaction, and a unique constraint instead of check-then-set. [Azure Idempotent Consumer#choose-a-stable-deduplication-key](https://learn.microsoft.com/en-us/azure/architecture/patterns/idempotent-consumer#choose-a-stable-deduplication-key), [#commit-the-processed-key-and-the-side-effects-atomically](https://learn.microsoft.com/en-us/azure/architecture/patterns/idempotent-consumer#commit-the-processed-key-and-the-side-effects-atomically), [#guard-against-concurrent-duplicates](https://learn.microsoft.com/en-us/azure/architecture/patterns/idempotent-consumer#guard-against-concurrent-duplicates)
- **AZ-7** A side effect that can't join the transaction (a Tempo POST, a Slack message) records in-progress, acts, then records completed; stale in-progress records are reconciled before retrying. Naturally idempotent operations are preferred first. [Azure Idempotent Consumer#handle-side-effects-that-cant-join-the-transaction](https://learn.microsoft.com/en-us/azure/architecture/patterns/idempotent-consumer#handle-side-effects-that-cant-join-the-transaction), [#problems-and-considerations](https://learn.microsoft.com/en-us/azure/architecture/patterns/idempotent-consumer#problems-and-considerations)
- **AZ-8** Outbox relay publishes unprocessed events then marks them processed, keeps order, deduplicates on message ID after relay retries, and expires old rows. The guide is Cosmos-specific; use the concepts. [Azure outbox#solution](https://learn.microsoft.com/en-us/azure/architecture/databases/guide/transactional-out-box-cosmos#solution), [#error-handling](https://learn.microsoft.com/en-us/azure/architecture/databases/guide/transactional-out-box-cosmos#error-handling), [#cleanup-and-maintenance](https://learn.microsoft.com/en-us/azure/architecture/databases/guide/transactional-out-box-cosmos#cleanup-and-maintenance)
- **AZ-9** A multi-step write that can partly fail has idempotent compensation steps, recorded progress, named points of no return, transient retries before compensating, and a human alert when automation can't recover. [Azure Compensating Transaction#solution](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction#solution), [#problems-and-considerations](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction#problems-and-considerations)
- **AZ-10** Security: a threat model exists and is maintained, the supply chain is scanned at build time, and an audit trail is kept. [Azure security#sustain-and-evolve-your-security-posture](https://learn.microsoft.com/en-us/azure/well-architected/security/principles#sustain-and-evolve-your-security-posture), [#design-to-protect-integrity](https://learn.microsoft.com/en-us/azure/well-architected/security/principles#design-to-protect-integrity), [#design-to-protect-confidentiality](https://learn.microsoft.com/en-us/azure/well-architected/security/principles#design-to-protect-confidentiality)
- **AZ-11** Infrastructure is abstracted away from domain logic, and architecture rules run as fitness functions in CI. [Azure design for change#recommendations](https://learn.microsoft.com/en-us/azure/architecture/guide/design-principles/design-for-evolution#recommendations)

## Google Cloud architecture and SRE (`google-cloud-architecture`)

Google's Architecture Center has no DDD guidance; use this lens for reliability, retries, idempotency and security.

- **GCP-1** Reliability targets come from user-experience goals and are realistic, never 100 percent. [Google WAF reliability](https://docs.cloud.google.com/architecture/framework/reliability), [SRE Workbook#reliability-targets-and-error-budgets](https://sre.google/workbook/implementing-slos/#reliability-targets-and-error-budgets)
- **GCP-2** An SLI, if defined, is good events divided by total events over a stated window, and its specification is separate from its implementation. [SRE Workbook#what-to-measure-using-slis](https://sre.google/workbook/implementing-slos/#what-to-measure-using-slis), [#moving-from-sli-specification-to-sli-implementation](https://sre.google/workbook/implementing-slos/#moving-from-sli-specification-to-sli-implementation), [#choosing-an-appropriate-time-window](https://sre.google/workbook/implementing-slos/#choosing-an-appropriate-time-window)
- **GCP-3** Retry budget: at most 3 attempts per request, and retries stay below about 10 percent of a client's requests. [SRE overload#deciding-to-retry](https://sre.google/sre-book/handling-overload/#deciding-to-retry-4ksZczHj)
- **GCP-4** Retry only at the layer directly above the one that rejected the request. [SRE overload#deciding-to-retry](https://sre.google/sre-book/handling-overload/#deciding-to-retry-4ksZczHj)
- **GCP-5** Backoff is randomized and exponential; permanent errors are not retried. [SRE cascading failures#retires](https://sre.google/sre-book/addressing-cascading-failures/#retires) (anchor spelled so on the site)
- **GCP-6** Deadlines are propagated from the caller, not invented per hop. [SRE cascading failures#deadline-propagation](https://sre.google/sre-book/addressing-cascading-failures/#deadline-propagation-1)
- **GCP-7** The design names what degrades gracefully (agent policy falls back to `RulePolicy`) and what fails fast. [SRE cascading failures#load-shed-graceful-degradation](https://sre.google/sre-book/addressing-cascading-failures/#xref_cascading-failure_load-shed-graceful-degredation)
- **GCP-8** An own API that creates resources takes a request ID (UUID4); a duplicate replays the earlier response within a dedupe window. For vendor APIs the vendor contract wins (coding-standards K3). [AIP-155](https://google.aip.dev/155)
- **GCP-9** Recovery from failures and from data loss is tested, and incidents get a postmortem. [Google WAF reliability](https://docs.cloud.google.com/architecture/framework/reliability)
- **GCP-10** Security is designed in and shifted left: checks run in the build, not only before release. [Google WAF security](https://docs.cloud.google.com/architecture/framework/security)

## DDD and hexagonal (`ddd-hexagonal`)

- **DDD-1** The domain knows no external component; ports are technology-agnostic; adapters translate one technology to a port and depend on the domain. [AWS hexagonal#implementation](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/hexagonal-architecture.html#hexagonal-architecture-implementation), [Microsoft Clean Architecture](https://learn.microsoft.com/en-us/dotnet/architecture/modern-web-apps-azure/common-web-application-architectures#clean-architecture)
- **DDD-2** Only the composition root (`cmd/timesheet/wire.go`) instantiates infrastructure types. [Microsoft#organizing-code-in-clean-architecture](https://learn.microsoft.com/en-us/dotnet/architecture/modern-web-apps-azure/common-web-application-architectures#organizing-code-in-clean-architecture)
- **DDD-3** A port and adapter pair is justified by several inputs or outputs, or a store expected to change; otherwise flag the extra layer. Full tactical DDD is for complex contexts; a supporting context may stay CRUD. [AWS hexagonal#issues](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/hexagonal-architecture.html#hexagonal-architecture-issues), [.NET DDD-oriented microservice](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/ddd-oriented-microservice)
- **DDD-4** Each bounded context has its own model, subdomains are classified core, supporting or generic, and the context map is documented (`docs/architecture/bounded-contexts.md`). [Azure domain analysis#define-bounded-contexts](https://learn.microsoft.com/en-us/azure/architecture/microservices/model/domain-analysis#define-bounded-contexts), [#example-drone-delivery-application](https://learn.microsoft.com/en-us/azure/architecture/microservices/model/domain-analysis#example-drone-delivery-application)
- **DDD-5** Aggregates are small (only the data one transaction must keep consistent), reference other aggregates by identity only, and are eventually consistent with each other. [Azure tactical DDD#aggregates](https://learn.microsoft.com/en-us/azure/architecture/microservices/model/tactical-domain-driven-design#aggregates)
- **DDD-6** The aggregate root is the only entry point for updates; aggregates are identified by their transactions. [.NET domain model#the-aggregate-root-or-root-entity-pattern](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/microservice-domain-model#the-aggregate-root-or-root-entity-pattern), [#the-aggregate-pattern](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/microservice-domain-model#the-aggregate-pattern)
- **DDD-7** Entities carry behaviour (an anemic model is an antipattern); value objects are immutable and the default choice. [Azure tactical DDD#entities](https://learn.microsoft.com/en-us/azure/architecture/microservices/model/tactical-domain-driven-design#entities), [#value-objects](https://learn.microsoft.com/en-us/azure/architecture/microservices/model/tactical-domain-driven-design#value-objects)
- **DDD-8** Application services orchestrate and hold no business rules. [Azure tactical DDD#domain-and-application-services](https://learn.microsoft.com/en-us/azure/architecture/microservices/model/tactical-domain-driven-design#domain-and-application-services), [.NET#the-application-layer](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/ddd-oriented-microservice#the-application-layer)
- **DDD-9** Domain events are past tense and immutable, collected in the aggregate and dispatched around the commit; integration events are asynchronous and only after the commit; handlers live in the application layer. [.NET domain events#implement-domain-events](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/domain-events-design-implementation#implement-domain-events), [#raise-domain-events](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/domain-events-design-implementation#raise-domain-events), [#domain-events-versus-integration-events](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/domain-events-design-implementation#domain-events-versus-integration-events)
- **DDD-10** One repository per aggregate root, its interface in the domain; only repositories write; one transaction per user action (unit of work). [.NET persistence#define-one-repository-per-aggregate](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/infrastructure-persistence-layer-design#define-one-repository-per-aggregate), [#implementing-unit-of-work](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/infrastructure-persistence-layer-design#implementing-unit-of-work)
- **DDD-11** Every external model (Slack, Jira, Tempo, Claude) is translated into the context's model by an ACL before it reaches the domain. [AWS PG ACL#intent](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/acl.html#acl-intent), [Azure domain analysis#example-drone-delivery-application](https://learn.microsoft.com/en-us/azure/architecture/microservices/model/domain-analysis#example-drone-delivery-application)
- **DDD-12** Go transactions use `BeginTx(ctx, ...)` with a deferred `Rollback`, never mix `Tx` and `DB` calls, and never issue raw `BEGIN` or `COMMIT`. [Go transactions#best_practices](https://go.dev/doc/database/execute-transactions#best_practices)

## Security architecture (`security-architecture`)

OWASP LLM IDs below are the **2026 edition** (published 2026-08-03). In the 2025 edition Excessive Agency was LLM06; always write `LLMnn:2026`. ASVS IDs are 5.0; 4.0 IDs are obsolete.

- **SEC-1** The threat model answers the four questions, draws trust boundaries on a data-flow diagram, uses STRIDE as prompts, gives every threat a response, and is kept current. [OWASP Threat Modeling#addressing-each-question](https://cheatsheetseries.owasp.org/cheatsheets/Threat_Modeling_Cheat_Sheet.html#addressing-each-question), [Microsoft STRIDE](https://learn.microsoft.com/en-us/azure/security/develop/threat-modeling-tool-threats)
- **SEC-2** Security requirements cite ASVS 5.0: V15.2 architecture and dependencies, V13.3 secret management, V16.2 and V16.4 logging, V16.5 error handling, V1 encoding and sanitization, V2 validation and business logic. [ASVS 5.0 index](https://cheatsheetseries.owasp.org/IndexASVS.html), [OWASP ASVS](https://github.com/OWASP/ASVS)
- **SEC-3** Assume the model's instruction boundary will be bypassed: every model response is validated against a strict schema in trusted application code, not by a second LLM call. [OWASP LLM01:2026](https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/2026/final/LLM01_PromptInjection.md)
- **SEC-4** External content reaches the model through a separate, provenance-labelled channel (`tool_result`). Prompt wording is not an enforcement boundary. [OWASP LLM01:2026](https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/2026/final/LLM01_PromptInjection.md), [Anthropic: mitigate prompt injection](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/mitigate-jailbreaks), [OWASP LLM cheat sheet#structured-prompts-with-clear-separation](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html#structured-prompts-with-clear-separation)
- **SEC-5** Credentials and state-changing capability stay in application code, not the model; actions are re-validated at execution time; writes to agent memory (lessons) are privileged. [OWASP LLM01:2026](https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/2026/final/LLM01_PromptInjection.md)
- **SEC-6** Agent tools are the minimum needed with minimum permissions and strict input schemas; authorization is decided in code (complete mediation); a human approves high-impact or externally visible actions. [OWASP LLM03:2026](https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/2026/final/LLM03_ExcessiveAgency.md), [OWASP LLM cheat sheet#human-in-the-loop-hitl-controls](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html#human-in-the-loop-hitl-controls)
- **SEC-7** Tool invocations have thresholds and a hard stop, and tool use is logged and monitored. [OWASP LLM03:2026](https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/2026/final/LLM03_ExcessiveAgency.md), [Anthropic: building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- **SEC-8** No secrets in system prompts; only task-required fields go to the model provider; logs and traces are scrubbed before they leave the process. [OWASP LLM02:2026](https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/2026/final/LLM02_SensitiveInformationDisclosure.md)
- **SEC-9** Model output rendered to a user (Slack) can't exfiltrate data: untrusted links and markdown images are blocked deterministically, and risky actions need user confirmation. [MSRC: indirect prompt injection](https://www.microsoft.com/en-us/msrc/blog/2025/07/how-microsoft-defends-against-indirect-prompt-injection-attacks), [Google: mitigating prompt injection](https://blog.google/security/mitigating-prompt-injection-attacks/)
- **SEC-10** MCP servers and tool packages are pinned and verified; dependencies are scanned at build time (`govulncheck` reports reachable vulnerabilities). [OWASP LLM01:2026](https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/2026/final/LLM01_PromptInjection.md), [Go vulnerability management](https://go.dev/doc/security/vuln/)
- **SEC-11** Defences are tested against adaptive attackers: injected-instruction fixtures for every untrusted source. A low attack success rate is still a risk. [OWASP LLM01:2026](https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/2026/final/LLM01_PromptInjection.md), [Anthropic: prompt injection defenses](https://www.anthropic.com/research/prompt-injection-defenses)

## Scale filter

Not a finding unless a requirement calls for it:

- Multi-region, multi-zone or disaster-recovery topologies; autoscaling; load balancers.
- Service mesh, API gateways per domain, or one microservice per bounded context. AWS names "too many microservices" as the drawback of decomposing by subdomain. [AWS decompose by subdomain](https://docs.aws.amazon.com/prescriptive-guidance/latest/modernization-decomposing-monoliths/decompose-subdomain.html)
- Sagas or orchestration across services: AWS reserves them for transactions that span services. Here one process writes one database. [AWS PG outbox#issues](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html#transactional-outbox-issues)
- CQRS read stores, event sourcing, separate query databases.
- Message brokers, broker-side deduplication, competing consumers. The in-process relay over the Postgres outbox covers AZ-6 to AZ-8.
- Load shedding and client-side throttling windows for many clients; a full SLO programme with stakeholder sign-off. One or two SLIs are enough.

Hexagonal everywhere or only where justified: the AWS hexagonal guide says always, the AWS pattern page and the .NET e-book say only where it pays off. Resolution: ports and adapters for the core timesheet context (ADR 0001); thin supporting code elsewhere (DDD-3, AZ-1).

**Circuit breaker vs retry budget.** AWS PG and Azure present the breaker as standard. The Builders' Library says use it "with caution" (modal behaviour, hard to test, slower recovery) and prefers a token-bucket retry limit. Hystrix is in maintenance mode in favour of adaptive concurrency limits. Azure itself calls it unsuitable when platform-level retries suffice. Resolution for timesheet-bot: no circuit breaker. Use the GCP-3 budget (at most 3 attempts), one retry layer (AWS-1, AZ-2), and a plain "stop after N consecutive failures and surface the error" counter, which also meets LLM03:2026 tool thresholds (SEC-7). A design that adds a breaker anyway must give it a manual override and log calls rejected while open. [Builders' Library](https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter), [Hystrix README](https://github.com/Netflix/Hystrix), [Azure Circuit Breaker#when-to-use-this-pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/circuit-breaker#when-to-use-this-pattern), [#problems-and-considerations](https://learn.microsoft.com/en-us/azure/architecture/patterns/circuit-breaker#problems-and-considerations), [AWS PG circuit breaker#issues](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/circuit-breaker.html#circuit-breaker-issues)

## Testing architecture

- **Sizes**: small tests run in one process with no sleep, I/O or blocking (domain, kernel, application with fakes); medium tests reach only `localhost` (Postgres in compose); large tests leave the machine. Aim for roughly 80/15/5. Flaky tests lose their value; retrying them is a stopgap. [SWE at Google ch. 11#test_sizes](https://abseil.io/resources/swe-book/html/ch11.html#test_sizes)
- **Unit tests** go through public APIs and test behaviours, not methods; no logic in tests. [SWE ch. 12#test_via_public_apis](https://abseil.io/resources/swe-book/html/ch12.html#test_via_public_apis)
- **Doubles**: prefer real implementations when fast and deterministic, otherwise fakes owned by the port's owner and tested against the real adapter (one contract test suite run on the fake and the Postgres repository); avoid interaction testing. [SWE ch. 13](https://abseil.io/resources/swe-book/html/ch13.html)
- **Larger tests** are hermetic and use record/replay for Slack, Jira, Tempo and Anthropic. [SWE ch. 14#larger_testing](https://abseil.io/resources/swe-book/html/ch14.html#larger_testing)
- **Fuzz** every parser of untrusted input (model output, vendor payloads): `FuzzXxx(*testing.F)` with one target, seed corpus in `testdata/fuzz`, fast and deterministic. [Go fuzzing#requirements](https://go.dev/doc/security/fuzz/#requirements), [#corpus-file-format](https://go.dev/doc/security/fuzz/#corpus-file-format), [#suggestions](https://go.dev/doc/security/fuzz/#suggestions)
- **Race**: `go test -race` finds only races that execute, so run it on tests that exercise the relay and scheduler concurrently; it needs cgo. [Race detector#Usage](https://go.dev/doc/articles/race_detector#Usage), [#Requirements](https://go.dev/doc/articles/race_detector#Requirements)
- **Coverage**: `-coverprofile` with `-covermode=set|count|atomic`; it measures unit-test coverage only. [Go blog: cover](https://go.dev/blog/cover). Our tests live in `test/` (ADR-0009), so coverage also needs `-coverpkg=./internal/...,./cmd/...`: by default a test measures only the package being tested (`go help testflag`).
- Design-level test obligations: duplicate requests (AWS-3), retry under failure (AZ-4), recovery (GCP-9), injected-instruction fixtures (SEC-11).

## Fitness functions

- A fitness function is an automated check on an architectural property, run like a unit test. [Thoughtworks Radar: architectural fitness function](https://www.thoughtworks.com/radar/techniques/architectural-fitness-function), [Azure design for change#recommendations](https://learn.microsoft.com/en-us/azure/architecture/guide/design-principles/design-for-evolution#recommendations)
- `test/architecture` (was `internal/archtest`; moved by ADR-0009) is ours. It reads the source of `internal/` and `cmd/`. `TestDependencyRules` enforces: domain and kernel import only the stdlib, the kernel and their own context; application does not import infrastructure, interfaces, platform or `cmd`; infrastructure does not import interfaces or `cmd`; interfaces never build adapters; no production package imports `timesheet-bot/test/...`. `TestDomainHasNoWallClock` bans the wall clock in the domain. Both run in `go test ./...` and `make arch`.
- Review checks: a design that adds a dependency rule or a context adds the matching rule in `test/architecture` in the same plan; a design that relaxes one needs an ADR. ADRs live in source control (`docs/adr/`). [Thoughtworks Radar: lightweight ADRs](https://www.thoughtworks.com/en-us/radar/techniques/lightweight-architecture-decision-records)
- Compiler-enforced `internal/` visibility is the only official Go mechanism. No official Go architecture linter guidance exists; go-arch-lint and depguard are third-party and not evaluated. [Go module layout](https://go.dev/doc/modules/layout)
