# Code map

How the code is organised and the flows that span several files. The diagrams are in [overview.md](overview.md), and the decisions in [ADR-0001](../adr/0001-ddd-package-by-bounded-context.md) and [ADR-0006](../adr/0006-personal-tool-scale-ready-aws-later.md).

## Dependency rule

DDD bounded contexts, package-by-context, Clean Architecture. Enforced only partly by the architecture tests in `test/architecture` (`make arch`), which also fail if production code imports `test/...`; the gaps are open findings M4, N1, N2 and N3 in the [conformance review](project-structure.md#conformance-review-2026-10-09).

- `internal/shared/kernel` is the shared kernel: `WeekID`, `WorkDay`, `IssueKey`, `Duration`, `WorkActivity`, `DomainEvent`, and the `Clock` port with `SystemClock`. Value objects are meant to be built through constructors: `NewDuration` enforces positive multiples of 15 minutes, and `NewWorkDay` rejects weekends. Their fields are unexported, but the zero-value literals `Duration{}` and `WorkDay{}` still bypass the constructors; `IssueKey` (a string type) and `WeekID` (exported fields) can also be built without validation. All of this is open finding L9. Validating external data, including future AI output, means constructing these types.
- `internal/<context>/domain` is pure Go and imports only the stdlib and the kernel. **No domain package imports another context's domain.** That is why `WorkActivity` lives in the kernel and not in `activity/domain`. Application layers may use another context's domain types; for example, `timesheet/application` uses `allocation/domain.Policy` and `Proposal`.
- `internal/<context>/infrastructure/*` holds the adapters. Ports are defined by the consumer. Timesheet's ports (`ActivitySource`, `IssueDirectory`, `WorklogGateway`) are in `internal/timesheet/application/ports.go`.
- `cmd/timesheet/wire.go` is the only composition root that knows the concrete adapters. `internal/interfaces/cli` takes a `Factory` and never builds adapters itself.
- Every Go test lives in `test/`, outside `internal/` and `cmd/`, and is black-box (`package x_test`) ([ADR-0009](../adr/0009-tests-in-separate-tree.md)). The tests for a package are in `test/<kind>/<area>/`; the mapping is in [testing.md](testing.md#layout-by-test-type).

## Key flows

- **Activity sources** (`activity/infrastructure/{slack,file}`): `activity.source` picks the `ActivitySource` in `wire.go`. `slack` searches with `SLACK_USER_TOKEN`; `file` reads `<activity.file_dir>/<ISO week>.json` written by the allocation-agent collector, after checking `schema_version`, `week` and `slack_user_id`. Both turn each message into a `kernel.WorkActivity` through `activity/domain.ToActivity` (day in the configured timezone, Jira keys, thread), so allocation never knows which source ran.
- **Report mode** (`allocation/domain/report.go`, `allocation/infrastructure/reportparser`): with `allocation.mode: report`, `wire.go` builds no Jira client and installs `ReportPolicy` instead of `RulePolicy`. Each message goes through `ReportParser.Parse` (`TODO(owner)`); `DedupReportLines` drops the lines the owner posted twice (channel and self-DM); every remaining line becomes a `ProposedEntry` with `Project`, which `build` adds with `Timesheet.AddReportEntry` (no Jira lookup, no cap check). Days over the cap become `Proposal.Warnings`, printed by `plan`. With `report.parser: llm`, `wire.go` sets `ProposeHandler.Reports` to the file collector and installs `ReportPolicy{Precomputed: true}`: the lines come from the activity file's `report_lines` (version 2, re-validated by `file.Collector.ReportLines`) through `alloc.Input.ReportLines`, and the hand-written parser is never called; dedup and warnings are the same. `kernel.ReportLine` is the shared type that crosses from Activity to Allocation. `MavenlinkMapping.Resolve(key, project)` places report entries by project (most specific rule wins: `issue_key`, `project`, `jira_project`; otherwise `default_workspace_id` with `Fallback` set, or an error). When Mavenlink is a submit target, `ProposeHandler.Placements` resolves every entry during `plan`: `ProposeResult.Placements` fills the `MAVENLINK` column, fallbacks become warnings, and an unmapped entry fails the plan ([ADR-0012](../adr/0012-report-mode-slack-summaries-to-mavenlink-without-jira.md)).
- **Propose** (`timesheet/application/propose.go`): collect activity, drop issue keys Jira doesn't know (such as `UTF-8`; skipped in report mode, where `Issues` is nil), then try `Policies` in order. Each proposal is replayed into a fresh `Timesheet` aggregate through `AddEntry`. The first one the aggregate accepts wins. Only aggregate rejections are added to `Input.Feedback` for the next policy; an error returned by `Allocate` itself is recorded as a `PolicyFailure` but not fed back (`propose.go:86-95`). This chain is how Phase 3 adds "agent, retry the agent with its errors, fall back to the rule" without special-case code ([ADR-0004](../adr/0004-allocation-policy-fallback-chain.md)).
- **Aggregate** (`timesheet/domain/timesheet.go`): only weekdays, every day inside the timesheet's week (`ErrDayOutsideWeek`), a daily cap, one entry per issue and day, and changes only in `draft`. The lifecycle is `draft -> awaiting_approval -> approved -> submitted`, with `rejected` reachable from `awaiting_approval`. Entry ids are deterministic (`<timesheetID>/<day>/<key>`). `Propose`, `Approve` and `Reject` each record an event; `MarkEntrySubmitted` records the id one target (`domain.Target`: Tempo or Mavenlink) gave an entry and no event; `CompleteSubmission(targets)` moves the timesheet to `submitted` and records `TimesheetSubmitted` once every entry is in every target; and `MarkEntryFailed` only at the final attempt (`MaxSubmitAttempts`). `Repository.Save` drains them with `PullEvents`.
- **Persistence** (`timesheet/infrastructure/postgres`): `Save` writes the row with an optimistic `version` check, replaces the entries, and appends the events to `outbox`, all in one transaction ([ADR-0002](../adr/0002-postgres-with-transactional-outbox.md)). Version 0 means insert. The `memory` repository is used by the tests in `test/unit/timesheet/application/`; its conflict check differs from Postgres (open finding L10). `wire.go` also installs it when no database is needed, but `plan --dry-run` never calls the repository.
- **Submit** (`timesheet/application/submit.go`): saves after **every** entry, so a retried `submit` skips entries already recorded as sent. It does **not** yet guarantee exactly-once: a crash between Tempo's success and the save, or a transport retry of the POST on 5xx, can still duplicate a worklog (open finding H2). Start times stack from 09:00 each day across *all* entries, including ones already submitted, so a retried entry keeps its slot.
- **Submit to Mavenlink** (`timesheet/application/submit.go`, `mavenlink_mapping.go`): runs after Tempo when `submit_targets` has `mavenlink`. It lists the week's entries carrying the tool's external reference and adopts them, places the rest with a `PlacementResolver` (`MavenlinkMapping.Resolve`, `TODO(owner)`), creates them, then sends one timesheet submission per project. A rejected credential (`application.ErrUnauthorized`) stops the run without touching any entry. Adapter: `timesheet/infrastructure/mavenlink`, with `Bearer` or `SessionCookie` auth ([ADR-0010](../adr/0010-add-mavenlink-as-a-second-submit-target.md)).
- **Migrations**: goose SQL files in `migrations/`, embedded through `migrations/embed.go` and run by `timesheet migrate up|down`.
