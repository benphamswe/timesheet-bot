## 2. Findings, ranked

### High

#### S1. `config.Secret` redacts only top-level `fmt` and slog values (F10, NFR-6)

- Where: plan section 4, Task 8.1 (`TestSecretLogValueRedacts`, "`config.Env` returns `map[string]config.Secret`").
- Leak scenario: the plan specifies only `LogValue` and `String`. With Go 1.26.9 (probe P3, P4), a string-kind `Secret` that has `String()` and `LogValue()` still prints the raw value in all of these cases:
  - `%#v` prints `"tok-SECRET"`, because fmt uses `GoString`, not `String`.
  - `%d` prints `%!d(main.Secret=tok-SECRET)`.
  - `%+v` of a struct that holds the secret in an unexported field prints `tok:tok-SECRET`.
  - `json.Marshal` prints `{"Token":"tok-SECRET"}`.
  - `slog.JSONHandler` prints `"nested":{"Token":"tok-SECRET"}` for a struct value, and `"m":{"k":"tok-SECRET"}` for the planned `map[string]config.Secret`.
  - `slog.TextHandler` prints an unexported field through `fmt.Sprint`.
- Why this happens:
  - slog resolves `LogValuer` only on attribute values. "If v resolves to a group, the group's attributes' values are not recursively resolved."
  - The JSON handler formats values "as with an encoding/json.Encoder", so it never calls `LogValue` inside a struct or a map.
  - The adapters keep the raw token in an unexported `token string` field (`tempo/client.go:24`, `jira/client.go:24`), so `fmt.Sprintf("%+v", client)` prints it.
- Reference: https://pkg.go.dev/log/slog (`Value.Resolve`, `JSONHandler.Handle`, `TextHandler.Handle`); OWASP Logging Cheat Sheet ("Access tokens", "Database connection strings" must not be logged).
- Fix (required plan change R1): see section 3.

#### S2. `APIError.Error()` includes `resp.Status`, which the server controls (NFR-6, F11)

- Where: Task 6.1 "Change": `Error()` = `"tempo: " + Status + ": " + Reason`. Task 6.2 does the same for Jira.
- Leak scenario: the reason phrase in the HTTP/1.1 status line is free text. A server, a proxy or a captive portal that answers `HTTP/1.1 400 tok-SECRET-123` puts that text in `resp.Status` (probe P5: `resp.Status="400 tok-SECRET-123"`). The plan redacts the token in `Reason` only. `Status` then flows unredacted into:
  - `err.Error()`;
  - `LastError` in `timesheet_entries.last_error`;
  - `Event.Reason` in the outbox `payload`;
  - the WP-8 Error log record;
  - the CLI's `error:` line.
- Why the test misses it: the planned `TestErrorsNeverContainSecrets` cannot catch this. `httptest`'s `ResponseWriter` always writes the standard reason text.
- Reference: RFC 9112 section 4, "A client SHOULD ignore the reason-phrase content because it is not a reliable channel for information" (https://www.rfc-editor.org/rfc/rfc9112#section-4).
- Fix (R2):
  - Build `Status` from `resp.StatusCode` and `http.StatusText(resp.StatusCode)`, never from `resp.Status`.
  - Test it with a raw `net.Listener` that writes a custom status line containing the canary token.

#### S3. The F16 URL check: `url.Parse` errors echo the password, and userinfo is not rejected

- Where: Task 4.2 (`TestTempoBaseURLMustBeHTTPS`, `config.HTTPSURL(name, raw)`) and Task 8.1 (`config.HTTPSURL(config.EnvJiraBaseURL, ...)`).
- Leak scenario: an operator sets `JIRA_BASE_URL=https://me%40corp.com:<token>@corp.atlassian.net`. Probes P1 and P2 show how it leaks:
  - `url.Parse` and `http.NewRequestWithContext` errors contain the whole raw string, password included: `parse "https://user:PW-SECRET@[bad": missing ']' in host`.
  - `net/http` client errors keep the username (`https://user:***@...`).
  - If `HTTPSURL` ever wraps the parse error, or lets a userinfo URL through, the secret reaches stderr and the logs.
- The plan's test list also misses these cases:
  - userinfo (`https://u:p@host`);
  - an opaque `https:host`, where `Host` is empty;
  - `https://:443`, where `Host` is non-empty but `Hostname()` is empty;
  - query and fragment, which break the `base + "/worklogs"` concatenation.
- Reference: RFC 9110 section 4.2.4, "a recipient SHOULD parse for userinfo and treat its presence as an error" and "the use of the format "user:password" is deprecated" (https://www.rfc-editor.org/rfc/rfc9110#section-4.2.4).
- Fix (R3). This answers the review question directly: yes, F16 must reject userinfo.

### Medium

#### S4. https-only base URLs are bypassed by a redirect to http

- Where: WP-2 owns `httpx.NewClient`. The plan sets no `CheckRedirect`.
- Leak scenario: the default `http.Client` follows up to 10 redirects. It forwards `Authorization` to "an exact match or subdomain" of the initial domain, and that match ignores scheme and port. Probe P7: an https server redirected to `http://127.0.0.1:<other port>`, and the client sent `Authorization: Bearer tok-SECRET-123` in cleartext. A misconfigured or compromised Tempo or Jira edge, or a typo-squatted base URL, can therefore downgrade the bearer and basic credentials.
- Reference: https://pkg.go.dev/net/http#Client (redirect header forwarding, `CheckRedirect`); OWASP SSRF Prevention Cheat Sheet ("Disable the support for the following of the redirection in your web client").
- Fix (R4).

#### S5. `tempo_base_url` comes from the YAML file and has no host allowlist

- Where: Task 4.2.
- Scenario: https-only still sends the Tempo bearer token to any https host named in `config.yaml`. The file is gitignored and mounted read-only, but it is copied between machines and edited by hand, unlike the env secrets. The plan already knows the only legitimate hosts: `tempo.DefaultBaseURL` and the two regional hosts.
- Reference: OWASP SSRF Prevention Cheat Sheet ("Match the host against an allowlist, and build the request yourself").
- Fix (R5).

#### S6. Migration 00002: legacy NULL-owner rows can never be updated, so the Phase 2 relay cannot mark them processed

- Where: plan section 3, `00002_outbox_owner.sql`; plan section 9, "the Phase 2 relay must tolerate them".
- Scenario: `NOT VALID` skips the scan, but the constraint "will still be enforced against subsequent inserts or updates". Probe P9 on PostgreSQL 17.11: after the plan's exact 00002 statements, `UPDATE outbox SET processed_at = now(), attempts = attempts + 1 WHERE aggregate_id = 'ts-deleted'` fails with `violates check constraint "outbox_user_account_id_set"`.
- Impact:
  - A relay that claims rows by `processed_at IS NULL` retries these orphan rows forever (a poison-row loop).
  - A relay that "tolerates" the rows by guessing an owner misroutes them. Under ADR-0006 seam 1, events are tenant-keyed.
- Reference: https://www.postgresql.org/docs/17/sql-altertable.html (`NOT VALID`); SQLSTATE `23514` `check_violation`, https://www.postgresql.org/docs/17/errcodes-appendix.html.
- Fix (R6). This also settles owner question Q2 from the security side: keep the rows, but close them.

#### S7. DSN password redaction edge cases (Task 7.3)

- Where: Task 7.3, `redact(err, password)` uses `strings.ReplaceAll`.
- Scenario 1, empty password: `strings.ReplaceAll(s, "", "[redacted]")` inserts the marker between every rune (probe P6). Errors become unreadable, and no test covers it. The compose DSN has a password, but a `.pgpass` or trust setup has none.
- Scenario 2, percent-encoding: a DSN password with reserved characters is percent-encoded in the URL (`p%40ss`). The parsed password is the decoded form, so an error that echoes the raw DSN text keeps the encoded form unredacted.
- Fix (R7).

#### S8. Reconcile against `GET /4/worklogs/user/{accountId}`: adoption rules and pagination need tightening

This answers the review question "can a crafted worklog make us skip a real post or mark the wrong entry?"

Skip a real post:
- Yes, in a narrow window. Reconcile runs only for entries with `NeedsReconcile()`, so only after an indeterminate attempt.
- Any worklog that the GET returns with equal issue, day, start, seconds and author is adopted, and the POST is skipped.
- Who can create such a worklog:
  - the owner;
  - anything holding the owner's Tempo token;
  - a Tempo user with "Log Work for Others" and "Manage Worklogs" (https://help.tempo.io/timesheets/latest/logging-time-for-others-in-the-timesheet).
- That user can already edit the owner's timesheet, so the extra risk is low. But adoption also takes a pre-existing hand-logged or someone-else-logged worklog that the owner may later delete, and the bot then believes the hours are logged.
- Severity low (residual). It is listed here because the cheap hardening below is a plan change.

Mark the wrong entry:
- Not reachable today. The slot (issue id, day, start) is unique per entry: `Entries()` sorts deterministically by day and key, and start times are staggered.
- There is one edge: two Jira keys that resolve to the same issue id (a moved issue) on the same day. `AddEntry` deduplicates by key, not by id.
- There is no invariant that a Tempo id is held by only one entry.

Pagination as a token-exfiltration vector:
- `PageableMetadata.next` is a full URL supplied by the server.
- The plan computes `offset` itself, which is correct, but it does not forbid requesting `next`. Following it would send the bearer token to whatever host the response names.
- Reference: OWASP SSRF Prevention Cheat Sheet ("Do not accept complete URLs from the user").

Fix: R8 (WP-6), R9 (WP-5) and R10 (WP-1).

#### S9. Security tests: unit-only in WP-6, absent in WP-11

- WP-6 `TestErrorsNeverContainSecrets`:
  - It checks only `err.Error()` for `Create` on 400 and 500.
  - It does not cover `ListByAuthor`, 401 and 403, the custom reason phrase (S2), `fmt.Sprintf("%+v", err)`, or the printed client struct (S1).
  - It does not cover `LastError` and the outbox payload, which are the persistence sinks.
- WP-11 E2E:
  - It contains no secret assertion at all.
  - It builds the App from adapters directly, bypassing `buildApp`, so F16 (https), F18 (`Needs` to env) and the `Secret` reveal path are never exercised end to end.
  - The https-only rule means an E2E through `buildApp` needs `httptest.NewTLSServer` and its `Client()`.
- Fix: R11 (WP-6) and R12 (WP-11).

#### S11. The BuildKit frontend `# syntax=docker/dockerfile:1` stays unpinned (F19)

- Where: `services/timesheet-core/Dockerfile:1`; Task 9.1 pins only the `FROM` images.
- Scenario: the syntax directive makes BuildKit "pull the latest stable version of the Dockerfile syntax before the build". That is a mutable tag running with access to the build context. F19's goal ("reproducible and tamper-evident") is not met while it floats.
- Reference: https://docs.docker.com/reference/dockerfile/#syntax; https://docs.docker.com/build/buildkit/frontend/ (`docker/dockerfile:1.2.1` is "immutable: never updated"; the directive accepts a `repo:tag@sha256:...` reference).
- Fix (R13).

#### S12. Task 9.1 pins `postgres:17` for compose, but compose runs `postgres:17-alpine`

- Where: plan section 0 row "Image digests" and Task 9.1 ("`postgres:17` (compose)"); `docker-compose.yml:3` is `postgres:17-alpine`.
- Scenario: writing `postgres:17@sha256:...` into compose silently swaps musl for glibc under the existing `pgdata` volume. The text indexes (`timesheets` primary key, `UNIQUE (user_account_id, week_id)`) were built under the old library's collation.
  - PostgreSQL: "A change in collation definitions can lead to corrupt indexes" (https://www.postgresql.org/docs/17/sql-altercollation.html).
  - The Alpine variant "does use musl libc instead of glibc" (https://github.com/docker-library/docs/blob/master/postgres/README.md).
  - A corrupt unique index can admit a second timesheet for the same owner and week, which breaks L10 and the H1 guarantees.
- Related: the Dependabot step is stale. `dependabot.yml` already has `docker` for `/services/timesheet-core` and `docker-compose` for `/`. Adding a `docker` entry for `/` (no Dockerfile there) is wrong.
- Fix (R14).

### Low

#### S10. Server text reaches the terminal and storage unsanitized

- `Reason` (`errors[0].message`) is server-controlled. The CLI prints errors with `fmt.Fprintln` (`cmd/timesheet/main.go:25`), so ESC, CR and LF sequences reach the terminal raw. The JSON handler escapes them; the plain `error:` line does not.
- Reference: OWASP Logging Cheat Sheet ("Perform sanitization on all event data to prevent log injection attacks", CR, LF and delimiters).
- Fix (R10b).

#### S13. Cache-mounted module download is not re-verified

- F20 adds `--mount=type=cache,target=/go/pkg/mod`.
- Fix (should, R15): add `go mod verify` after `go mod download`, so a stale or poisoned cache entry fails the build against `go.sum`.

#### S14. `submit --retry-rejected` leaves no audit trail

- `ReopenRejected` clears every `SubmitRejected` flag and returns a count. It records no event and no log.
- The command is otherwise safe:
  - reopened entries keep `SubmitAttempts > 0`, so `NeedsReconcile()` forces the GET before any POST;
  - a repeated 4xx just re-rejects;
  - it is owner-scoped through `TransitionHandler.UserAccountID`.
- Reference: OWASP Logging Cheat Sheet (state-changing and administrative actions).
- Fix (R9c).

#### S15. F18 has a CLI-level test but no wiring-level test

- `TestCommandsRequestOnlyWhatTheyNeed` checks the `Needs` value only. Nothing proves that `buildApp` with only `DATABASE_URL` set lets `approve` run, or that `submit` never reads `SLACK_USER_TOKEN` or `JIRA_API_TOKEN`.
- Residual: `docker-compose.yml` passes all five variables to every `docker compose run`. Process-level least privilege then depends on the shell. Note this in the threat model rather than changing it in SP-01.
- Fix (R16).

#### S16. N4 gaps at the aggregate

- `AddEntry` gains key, id and duration checks. It still accepts:
  - an unbounded or non-printable `description`, which is sent to Tempo and visible to the manager;
  - a second entry with the same `issueID` on the same day under a different key.
- `NewTimesheet` checks only that the owner is non-empty.
- The description is bot-generated today (`rule.go:58`), but P3 makes it LLM output, which is untrusted per threat model boundary 2.
- Reference: OWASP Input Validation Cheat Sheet ("Validate both syntax ... and semantics"; "Length limits and the characters or structure required by the field").
- Fix (should, R17).

#### S17. The runtime database role is a superuser (residual, out of scope)

- `POSTGRES_USER` "will create the specified user with superuser power" (https://github.com/docker-library/docs/blob/master/postgres/README.md). The app and the migrations both connect as `timesheet`.
- All SQL is parameterized, so there is no current exploit path.
- Record it in the threat model. A separate migration role and DML-only runtime role belong to Phase 2, not SP-01.

#### S18. Defense in depth for the logger

- The plan relies on every call site passing safe values. Fix (R18, should):
  - give the JSON handler a `ReplaceAttr` that drops attributes whose key matches `(?i)(token|secret|password|authorization|dsn|database_url)`. `ReplaceAttr` "is called to rewrite each non-group attribute"; a zero `Attr` discards it;
  - add an archtest rule that only `cmd/timesheet` may call `Secret.Reveal`.

## 3. Required plan changes

Each item names the WP and task that owns it. "Must" items are conditions for the verdicts above; "should" items are recommended but not blocking.

- **R1 (must, WP-8 Task 8.1).** Define `Secret` as a struct with an unexported field, not a string kind: `type Secret struct{ v string }`, with `func (s Secret) Reveal() string`.
  - Implement `String`, `GoString`, `Format(fmt.State, rune)`, `LogValue`, `MarshalJSON` and `MarshalText`, all returning `[redacted]`.
  - Never log the `config.Env` map, and never put a `Secret` or a revealed value in a struct that is logged.
  - Extend `TestSecretLogValueRedacts` to assert that the canary is absent from all of these:
    - `fmt` with `%v`, `%+v`, `%#v`, `%s`, `%q`, `%x` and `%d`;
    - `%+v` of a struct holding a `Secret` in an exported field and in an unexported field;
    - `json.Marshal` of the struct and of `map[string]Secret`;
    - `slog` JSON and Text handlers with the `Secret` at the top level, nested in a struct, in a map and in `slog.Group`.
  - Unexported-field printing cannot be fully prevented by the type. The adapters therefore must not store the raw token: R11 changes them.
- **R2 (must, WP-6 Tasks 6.1 and 6.2).** `APIError.Status` is `strconv.Itoa(code) + " " + http.StatusText(code)`. Never use `resp.Status`. Add `TestReasonPhraseNeverReachesError`: a raw `net.Listener` answers `HTTP/1.1 400 <canary>`, and neither `err.Error()` nor `%+v` contains the canary. Order the `Reason` pipeline as:
  1. read at most 4 KB;
  2. extract `errors[0].message`;
  3. redact every credential form: token, `Bearer `, `Basic ` and base64(`email:token`);
  4. strip non-printable runes (R10b);
  5. truncate to `MaxReasonLen` runes.

  Redaction must come before truncation, so a cut never leaves a partial secret.
- **R3 (must, WP-4 Task 4.2).** `HTTPSURL(name, raw)`:
  - Parse with `url.Parse`. On error, return `fmt.Errorf("%s is not a valid URL", name)` without wrapping or quoting the parse error.
  - Reject when any of these hold: `Scheme != "https"`; `Hostname() == ""`; `User != nil` (RFC 9110 4.2.4); `Opaque != ""`; `RawQuery != ""`; `Fragment != ""`.
  - Apply the same function to `tempo_base_url`.
  - Add test rows: `https://u:<canary>@host`, `https://u:<canary>@[bad`, `https:api.tempo.io`, `https://:443/4`, `https://api.tempo.io/4?x=1` and `https://api.tempo.io/4#f`. Every error names the variable and contains neither the canary nor the raw value.
- **R4 (must, WP-2 Task 2.1).** `httpx.NewClient` sets `CheckRedirect` to refuse every redirect. Tempo and Jira REST and Slack Web API calls never need one, so return `http.ErrUseLastResponse`, and let the adapter classify the 3xx as a plain `*APIError`. Add `TestClientDoesNotFollowRedirects`: an https server redirects to an http server, and the http server receives no request. If a redirect is ever needed, the minimum rule is: same scheme `https`, same host, and strip `Authorization` otherwise.
- **R5 (must, WP-4 Task 4.2).** `tempo_base_url` must have a host in `{api.tempo.io, api.eu.tempo.io, api.us.tempo.io}`. Error example: `tempo_base_url host is not a Tempo API host`. Tests point at `httptest` through the constructor, not through the YAML file. For `JIRA_BASE_URL`, should require a host ending in `.atlassian.net`; ask the owner whether a custom Jira Cloud domain is in use before making this a must.
- **R6 (must, WP-7 Task 7.1).** Change `00002_outbox_owner.sql` so that, after the backfill and before `ADD CONSTRAINT`, it closes the orphans:

  ```sql
  UPDATE outbox SET processed_at = now()
  WHERE user_account_id IS NULL AND processed_at IS NULL;
  ```

  These rows belong to timesheets that an earlier `plan --force` deleted, and no relay exists yet. Keep them as history, never deliver them, and never update them again. Document in the migration comment that a NULL-owner row is closed and immutable. Extend `TestMigrateDownUpOnFreshDatabase`:
  1. `up` to version 1;
  2. insert one outbox row for a missing timesheet;
  3. `up` to version 3;
  4. assert the row has `processed_at IS NOT NULL`;
  5. assert an `INSERT` without an owner fails with `23514`.

  The Down migration is unchanged.
- **R7 (must, WP-7 Task 7.3).** `redact`:
  - returns the error unchanged when the password is empty;
  - replaces the decoded password, its `url.QueryEscape` form and its `url.PathEscape` form.

  Add cases to `TestOpenErrorHidesPassword`: a password with `@`, `%` and `:`; an empty password; and a keyword/value DSN (`host=127.0.0.1 port=1 user=u password=<canary> dbname=db connect_timeout=1`).
- **R8 (must, WP-6 Task 6.1).** `ListByAuthor`:
  - never requests the `metadata.next` URL. It builds every page URL from the configured base, the escaped account id and its own `offset`. Assert this in `TestListByAuthorPaginates` by setting `next` to an absolute URL on a second `httptest` server that must receive zero requests.
  - decodes each page through `io.LimitReader(body, 1<<20)` and drains it.
  - skips any result with `tempoWorklogId <= 0`, `issue.id <= 0`, or `author.accountId` not equal to the requested account id.
  - applies the R2 error rules.
- **R9 (must, WP-5 Task 5.1).**

  - (b) Log every adoption at Info (`tempo worklog adopted`, `entry_id`, `worklog_id`), so a wrong adoption can be audited.
  - (c) `ReopenRejected` records a domain event (for example `EntriesReopened`, with owner, week and count) and an Info log. The domain part is in WP-1 (R10c).
  - (d) Should: persist the attempt start (`submit_attempted_at timestamptz` in 00003), and adopt only worklogs whose Tempo `createdAt` is at or after that time minus 5 minutes. That excludes pre-existing hand-logged or third-party worklogs. This also answers Q4 from the security side: prefer the `createdAt` window over a `description` match, because a description is editable by the manager and the window is not.
- **R10 (must, WP-1 Tasks 1.1 and 1.2).**

  - (b) The `MaxReasonLen` truncation helper used for `LastError` and `Event.Reason` first replaces every rune with `!unicode.IsPrint(r)` by a space, then truncates. Add a test with `"\x1b[2J\r\nfake"`.
  - (c) The `ReopenRejected` event from R9c.

  - Adapters store an authorizer (`auth func(*http.Request)`, built in the constructor) instead of `token string`, `email string`. `fmt` prints a func as an address.
  - Add `TestClientPrintsNoSecret`: `fmt.Sprintf("%v %+v %#v", c, c, c)` contains no canary.
  - Extend `TestErrorsNeverContainSecrets` to `ListByAuthor`, to 401 and 403, and to `%+v` of the error.

## 5. Checks found clean

- `config.Env` reports missing variable names only (`internal/config/config.go`, `Env`).
- The Tempo account id is escaped with `url.PathEscape` in the planned `ListByAuthor`, and the Jira key with `url.PathEscape` today (`jira/client.go:51`).
- Every SQL statement in `postgres/repository.go` and the planned `Delete` is parameterized.
- The planned `Delete` checks submissions under `SELECT ... FOR UPDATE` in the same transaction, so the check and the delete cannot race.
- F6 wraps driver errors with `%v`. `pgconn.PgError.Error()` does not include `Detail`, so row contents (probe P9 shows that DETAIL echoes the full row) stay out of application errors.
- The retry rule follows RFC 9110 9.2.2: no retry of POST on 5xx or on transport errors; only `WithReadOnly` for Slack search.
- Bounded reads: 4 KB error body, 1 MB success body, 64 KB drain.
- Session timeouts are set per session through `RuntimeParams`, not in `postgresql.conf`, which the PG 17 docs advise against for `statement_timeout`. Migrations use a separate `sql.DB`, so a 5 s limit does not hit long DDL.
- F15: the second Ctrl-C restores default signal handling. K1 (attempt saved before the POST) makes a hard kill safe, because the next run reconciles.
- `.dockerignore` excludes `config/config.yaml`, `bin/` and `*.out`. The final image copies only the binary, and the smoke test asserts `nonroot:nonroot`.
- `govulncheck` (module toolchain go1.26.9): `No vulnerabilities found.`

## 6. Residual risks after the required changes

- An insider with "Log Work for Others" and "Manage Worklogs" can still create a matching worklog inside the reconcile window. Low: they can already edit the owner's timesheet.
- A 429 that Tempo answers after storing a worklog would duplicate it (plan section 9, accepted).
- Environment variables are readable by same-user processes. The OWASP Secrets Management Cheat Sheet notes that environment variables "are generally accessible to all processes". Accepted for a single-user laptop tool (threat model, residual risks).
