## Summary

The exactly-once design is sound. It saves an attempt marker before each POST, treats an unknown outcome as indeterminate and reconciles before any re-post. It follows the AWS Builders' Library guidance for creates without a client token. The retry policy matches the Google SRE book and the AWS Builders' Library: 3 attempts, randomized backoff, one retry layer, and no retry of permanent errors. The Postgres changes are safe on an existing database.

The plan cannot go final yet. These gaps block it:

1. **Rollback is not planned, and the documented order is wrong.** The 00002 `CHECK ... NOT VALID` still applies to new inserts, so the pre-SP-01 binary fails every save that writes an outbox event. The old binary also cannot run `migrate down` for versions 2 and 3: goose returns `ErrVersionNotFound` because the old image does not embed those files. `docs/operations/deployment.md:32` says to rebuild the previous image first and then run `migrate down`. That order must be reversed.
2. **No operations docs are in scope.** Task 11.3 updates architecture and API docs but no runbook. `submit-partial-failure.md` becomes wrong after this plan, the unknown-outcome and rejected-entry runbooks do not exist, and `slo.md` and `failure-modes.md` have never been written.
3. **Observability cannot correlate a run.** WP-8 has no run id and no `week_id` or `timesheet_id`, no run summary record, and no record when an entry is reconciled.
4. **Some submit failure paths are not pinned by tests.** These are a failed marker save, Ctrl-C during the POST, and a reconcile that matches a worklog that is already linked to another entry.
5. **WP-9 would change the Postgres base image on an existing data volume.** It would move from `postgres:17-alpine` (musl) to `postgres:17` (glibc), which risks invalid text indexes.

Each fix is small. The exact changes are listed per WP below.

## 1. Exactly-once submit

### What makes it work

- **Deterministic slots.** Reconcile matches on `StartTime`, and the start time is derived from the walk order. That order is deterministic, because `Timesheet.Entries()` sorts by day and then issue key (`internal/timesheet/domain/timesheet.go:108-118`), even though the Postgres `Get` has no `ORDER BY` (`postgres/repository.go:51-53`). The schema also guarantees one entry per issue and day: `UNIQUE (timesheet_id, issue_key, day)`, `migrations/00001_init.sql:28`. So `(IssueID, Day, StartTime)` is unique within a timesheet.
- **Optimistic locking guards concurrent runs.** Two terminals that both run `submit` both read version N. The second marker save gets `ErrConcurrentModification` (`postgres/repository.go:100-109`), so that run stops before it can POST.
- **Legacy entries benefit.** Pre-SP-01 failed entries have `submit_attempts > 0` and no Tempo id, so `NeedsReconcile()` is true after the upgrade. The first new `submit` looks them up before it posts. This also catches worklogs that the old 5xx POST retry (`httpx/retry.go:53,77-79`) may already have created.

`context.WithoutCancel` behaves as the plan assumes: "returns a derived context that points to the parent context and is not canceled when parent is canceled ... returns no Deadline or Err" (pkg.go.dev/context). The plan wraps it in `WithTimeout` and calls `cancel`, as the same page requires: "code should call cancel as soon as the operations running in this Context complete".

Answers to the plan's questions in my area:

- **Q4: do not require an equal `description`.** The submit-correctness SLO counts duplicates and losses equally. A stricter match turns E3 into a duplicate whenever Tempo or the owner changes the text. Adopting a hand-logged identical slot logs the same time once, which is the outcome the owner wants.
- **Section 9, the 429 on POST: accept.** The retry happens before any marker can help. RFC 9110 and coding-standards R3 allow it. Record it in `failure-modes.md` and consider R1.
- **Q3: keep the explicit `--retry-rejected`.** A block that clears itself would re-post a permanent 4xx on every run and hide it inside the "failed" count.

## 2. `plan --force` (H1)

The guard is correct. `Discard` refuses when the timesheet is submitted, when an entry has a Tempo id, or when an entry has `SubmitAttempts > 0` and is not `SubmitRejected`.

The replace is atomic as specified. Section 2 says `Replace` deletes `previous` by id, owner and version, inserts `next` and writes both event streams in one transaction. Task 7.2 refers to section 2. `TestReplaceInsertFailureRollsBackDelete` proves the rollback.

The race with a concurrent `submit` is closed by the version predicate. Under Read Committed, a second updater that finds a deleted row "will ignore the row if the first updater deleted it" (PostgreSQL 17, transaction-iso). So whichever commits second gets `ErrConcurrentModification`. If `submit` loses, it loses on its marker save, before any POST.

Two operator gaps:

- **The refusal is permanent until `submit` settles the entries.** This covers an entry that got a 401, and an unknown outcome that the owner chooses to re-plan instead of submit. `ErrHasSubmissions` today gives the owner no counts and no next step (S1, S14).
- **Legacy entries that failed with a permanent 400** (for example a deleted issue) are not `SubmitRejected` after 00003. They therefore block `plan --force` until one new `submit` marks them rejected. `submit-partial-failure.md:17` currently tells the owner to `plan --force` in that case, and it will be refused (runbook change RB-1).

## 3. Event drain after commit (M5)

This is correct. `MarkPersisted` runs only after `BeginFunc` returns nil, and pgx returns the commit error. If the commit outcome is unknown, the events stay pending and the version stays old. A retry of the same object cannot duplicate outbox rows: an update fails the `version = $n` predicate, and an insert fails with `23505`. Both map to `ErrConcurrentModification`, and the whole transaction rolls back. Submit returns on any save error and re-reads on the next run.

One gap: the plan does not say that `Replace` calls `MarkPersisted` on both aggregates after commit, and no contract subtest checks it (S2).

The Phase 2 relay must still treat outbox rows as at-least-once. Record this in `failure-modes.md`.

## 5. Observability (WP-8)

The design is right at this scale: stdlib slog, JSON on stderr, one logger built in `main`, no metrics stack. The levels are reasonable: Warn per retry, Error per final create failure. A nil `HandlerOptions.Level` means Info: "If Level is nil, the handler assumes LevelInfo" (pkg.go.dev/log/slog).

Gaps:

- **No correlation.** Nothing ties the retry, create and save lines of one run together, or ties them to a week. The agent's review checklist requires `week_id` and `timesheet_id` on each run's slog lines.
- **No audit of exactly-once decisions.** Adopting a worklog during reconcile (E3) leaves no log line, so a wrong adoption (E12, E13) cannot be found afterwards.
- **No run outcome record.** Nothing at Info records the counts and the duration, so the submit-latency SLI cannot be read from logs.
- **Silent retry decisions.** When the transport returns a 429 or 503 without sleeping, because of the deadline (F3), nothing says so.

S12 and S13 close these.

## 6. Docker smoke test (WP-10, WP-9)

The three checks are sound. I traced each of them:

- `CMD ["--help"]` exits 0.
- The Dockerfile sets `USER nonroot:nonroot`, so `.Config.User` equals the string the test expects.
- `config.example.yaml` passes `resolve`: `REPLACE_ME` is non-empty, the channel keys are valid, and the Tempo URL is https. `buildApp` calls `config.Load` before `config.Env` (`cmd/timesheet/wire.go:26-41`), so the time zone is resolved before the missing `DATABASE_URL` is reported.

Gaps:

- **"Non-zero exit" also matches Docker's own failures.** Docker documents its own codes: "Exit code 125 indicates that the error is with Docker daemon itself", 126 means the command "can't be invoked", and 127 means it "can't be found" (docs.docker.com, Running containers). Assert exit code 1 (S18).
- **The image never runs `migrate up`.** N-07 changes the embed path. A missing file fails `go:embed` at compile time, so the risk is low. A `migrate up` against a throwaway Postgres would still prove that the shipped image can upgrade (recommendation R3).

## 7. Second Ctrl-C (WP-4, note O1)

In the container the binary is PID 1. A process in an ancestor namespace can signal PID 1 "only if the "init" process has established a handler for that signal" (man7 pid_namespaces(7)).

After `stop()`, Go's own runtime handler stays installed. Its `dieFromSignal` falls back to `exit(2)` when the re-raised signal is ignored (`runtime/signal_unix.go`, `dieFromSignal`). So a second Ctrl-C does end the process under Docker, with exit status 2. That is acceptable, because the next run reconciles (E9). Do not write `130` into the runbooks.

## 10. Recommendations (not blocking)

- **R1. Duplicate audit after submit.** After a run that posted anything, call `ListByAuthor` once and warn about any `(IssueID, Day, StartTime)` with more than one worklog by the author. This detects E11 and E12. It also gives the "0 duplicate worklogs" SLI a measurement. One GET per run fits P10.
- **R2. Save timeout.** Use 5s instead of 10s for the `WithoutCancel` saves. `statement_timeout` is 5s already, and the `docker stop` and compose `stop_grace_period` default is 10s before SIGKILL. If the save outlives the grace period, the result is E9, which is safe, but the timeout should fit inside the grace period.
- **R3. Migrate smoke.** In `make smoke`, also run `migrate up` against a throwaway `postgres:17-alpine` container on a private Docker network, and expect `migrate up: ok`.
- **R4. Replace guard in SQL.** In `Replace`, also run the `EXISTS` submissions guard that `Delete` uses. The version predicate already covers the race; the guard costs one query.
- **R5. Legacy attempt counts.** Pre-SP-01 entries can already have `SubmitAttempts >= 3`. The `== MaxSubmitAttempts` rule then never emits `EntrySubmissionFailed` for them. The Phase 2 failure DM should not depend on that event alone.
